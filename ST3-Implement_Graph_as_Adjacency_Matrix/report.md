# Standard Task 3 : Implement Graph as Adjacency Matrix

The implementation models an undirected graph using a 2-D adjacency matrix. Because the task fixes vertex identifiers as positive integers while Python lists are zero-indexed, the class maintains an explicit mapping `vertex id v → matrix index v − 1`. This mapping is the single most error-prone aspect of the task, and the helper `_check_vertex` centralises validation so that invalid ids raise an exception before any mutation occurs. Treating the graph as undirected is justified by the example matrix, which is symmetric; consequently `add_edge` and `remove_edge` update both `M[v1−1][v2−1]` and `M[v2−1][v1−1]`, preserving symmetry as an invariant.

The four required methods have deliberately different cost profiles. `add_edge` and `remove_edge` are \(O(1)\) because adjacency matrices support constant-time edge access (Goodrich & Tamassia, 2015). `print_matrix` is \(O(n^2)\) because every cell is rendered, and the alignment logic is factored into a single formatting pass rather than scattered `print` calls. `add_vertex` is the expensive operation: growing the matrix requires appending columns to every existing row and appending new zero rows, which is \(O(n^2)\) time and space. The method accepts an optional id and expands the matrix to that id if necessary, so the class tolerates non-contiguous numbering rather than forcing sequential insertion.

Two additional analytical functions are provided. `transitive_closure` implements Warshall's algorithm (Warshall, 1962), which determines reachability between every ordered pair of vertices in \(O(n^3)\) time. A critical detail is that the algorithm copies the matrix before running: Warshall's algorithm mutates its input in place, so operating directly on `self.adjMatrix` would overwrite the original graph and corrupt subsequent queries. The copy restores the original matrix's role as a persistent representation of the network. `degree_sequence` computes the row sums in \(O(n^2)\) and returns either the vertex-order degrees or a descending sequence, which is a standard graph invariant used for isomorphism testing and connectivity analysis (West, 2001).

From a design standpoint, the code is compact and readable: the class exposes a small, orthogonal API, and the printing logic is isolated from the algorithmic logic. The main trade-off is the choice of an adjacency matrix itself. Matrices give \(O(1)\) edge lookup and are natural for dense graphs, but they consume \(O(n^2)\) memory even when few edges exist. The transportation network in the task has six or seven vertices, so this waste is negligible; for a sparse network with thousands of hubs, an adjacency list would reduce memory to \(O(n+m)\) at the cost of slower edge queries. This is the classic dense-versus-sparse trade-off (Cormen et al., 2009), and the task's explicit demand for a matrix display legitimises the matrix choice.

A second critical point is that `add_vertex` scales poorly. Because the matrix is stored as a list of lists, extending it is inherently \(O(n^2)\). A more elegant Python approach would store the matrix as a `dict` of `dict`s keyed by vertex id, giving \(O(1)\) edge access and amortised \(O(1)\) vertex insertion, at the cost of losing the uniform \(n \times n\) layout needed for Warshall. An alternative is to over-allocate capacity, but this complicates the printing routine. Given the teaching context and the small \(n\), the straightforward growth strategy is defensible and keeps the code transparent.
