# Assessed Advanced Task 3/3: Implementation of a Concurrent, Fault-Tolerant Headline Scraper

The system implements a two-tier concurrent headline scraper. The primary backend is **newspaper3k**, which performs a full-site scan and applies its own content heuristics; the secondary backend is a **requests + BeautifulSoup** fallback, positioned explicitly as a safety net rather than a peer. The concurrency layer uses `concurrent.futures.ThreadPoolExecutor`, each call is wrapped in a daemon thread joined with a hard deadline, and the resilience layer adds per-domain rate limiting and exponential-backoff retries with jitter.

The asymmetric roles of the two backends justify the design. `newspaper.build()` discovers candidate article URLs, downloads and parses each one, and validates the result against content heuristics — it is the source of truth for what counts as a headline. Its cost is time: on the seven-URL test set it consumed 15–131 seconds per site, with CNN and Spiegel at the upper end. The BS4 fallback exists only to guarantee that the scraper still returns *something* when newspaper fails, times out, or returns an empty list. It issues a single HTTP request, strips structural chrome (`nav`, `header`, `footer`, `aside`, `form`), removes elements whose class or id hints at navigation, then applies an `href`-structure filter and a text-quality filter. Its speed advantage is substantial — foxnews completed in 10.4 seconds via BS4 against 130.9 seconds for CNN via newspaper — but this speed comes at a quality cost: BS4 cannot validate that an anchor is actually an article, only that it *looks* like one. The final `fetch_methods` distribution was `{newspaper: 6, bs4: 1}`, confirming BS4 as a genuine fallback rather than the main path.

The default URL list was adjusted for the network environment in which the experiments ran. Two mainland-China accessible sources (Sina News and NetEase News) were added alongside the five international sources, because the international sites are unreachable or extremely slow from a mainland connection without a VPN. The two Chinese sources served as the primary workload for verifying concurrency, timeout handling, retries, and export logic independently of international link quality, while the international sites continued to exercise the timeout and fallback paths. This mixed set is more representative of real deployment conditions, where a scraper often has to operate under heterogeneous network reachability.

The choice of `ThreadPoolExecutor` over `ProcessPoolExecutor` is deliberate and grounded in the workload characteristics. Headline scraping is I/O-bound: the CPU spends nearly all its time waiting on network responses, and the GIL is released during blocking I/O, so threads achieve genuine parallelism without process overhead. `ProcessPoolExecutor` would pay a significant startup cost per worker — spawning a fresh interpreter, importing newspaper, lxml, Pillow, and BeautifulSoup — and would duplicate memory per process. It would also break the `DomainRateLimiter`, which relies on a shared `threading.Lock` that cannot be pickled across process boundaries. Empirical results support the decision: with 8 workers, wall-clock time was 130.5 seconds against a serial baseline of 308.5 seconds, a 2.36× speedup. The speedup is bounded by the slowest single URL (CNN at 130.9 seconds), not by the worker count, which is a direct illustration of Amdahl's law: with seven URLs and eight workers, the wall-clock time is dominated by one long-running task rather than by aggregate throughput.

Both backends have known weaknesses. The newspaper backend achieved 31/35 correct titles (88.6%); the four false positives split into podcast landing pages (CNN's *All There Is* and *Terms of Service*, whose show notes exceed the body-length filter) and section hubs (BBC's *Entertainment & Arts* and *Latest News & Updates*, whose URLs satisfy the href-structure heuristic). The BS4 fallback is faster but structurally blind: it cannot tell an article anchor from a navigation anchor, only a plausible one, which is why the DOM-cleaning and href-filtering rules are so extensive. Both share a deeper limitation: their filtering logic is hand-crafted and static. Every new site potentially requires new reject prefixes, new URL segments, and new body-length thresholds.

This is where a large language model could replace manual filtering with semantic judgement. Having built the next-generation agent system at China Telecom, I have seen this shift first-hand: what starts as a growing list of regex rules eventually becomes a small LLM call that returns a structured verdict. For this scraper, an LLM could be invoked on each candidate `(title, url, body_excerpt)` tuple and asked a single question — "is this a news headline for an article page, yes or no?" — returning a JSON object with a confidence score. The advantages are semantic robustness across languages and site layouts, the ability to reject podcast pages and section hubs without site-specific rules, and graceful handling of unusual formats. The costs are latency (one model call per candidate unless batched) and non-determinism, which complicates benchmarking. A hybrid design mitigates this: keep the deterministic filters for the obvious cases (chrome, empty body, known non-article URL patterns) and reserve the LLM for the ambiguous middle where the current system silently fails — exactly the CNN podcast and BBC section-hub cases observed here. Batching all candidates from a single site into one prompt amortises latency, and constraining the output to a strict schema keeps it parseable. From my experience, the most valuable property of LLM-based filtering is not raw accuracy but *legibility*: each rejection can be logged with a natural-language reason, turning a black-box filter into an auditable one. That is a genuine engineering gain when a scraper has to be maintained across dozens of sources with shifting layouts.
