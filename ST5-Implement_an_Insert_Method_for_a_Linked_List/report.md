# Standard Task 5: Implement an Insert Method for a Linked List

The `Insert` method locates the first node whose `dataval` equals `val_before`, then splices a new node immediately after it. The core pointer operation is two assignments: `new_node.nextval = current.nextval` followed by `current.nextval = new_node`. This order is essential; reversing it would lose the remainder of the list. The method handles four boundary cases explicitly. If `val_before` is `None`, it prints a message and returns. If the list is empty (`self.headval is None`), it refuses the insertion because there is no node to insert after. If the search reaches `None` without a match, it reports that the value was not found. Inserting after the final node requires no special branch: when `current` is the tail, `current.nextval` is already `None`, so the new node naturally becomes the new tail. This uniformity is a sign of a clean linked-list design (Sedgewick & Wayne, 2011).

Two additional functions improve robustness. `Search` walks the list and returns a Boolean, running in \(O(n)\) time and \(O(1)\) space. `Delete` removes the first node with a given value. Its three cases are worth noting: deleting the head updates `self.headval` in \(O(1)\); deleting an interior or tail node requires a `prev` pointer so that `prev.nextval = current.nextval` bypasses the removed node, which costs \(O(n)\) to locate. All three operations therefore run in \(O(n)\) worst-case time and use constant extra space.

From a critical perspective, the method's cost profile is inherent to singly linked lists. Locating the predecessor is \(O(n)\), so insertion is not constant-time despite the actual splice being \(O(1)\). A doubly linked list would make deletion of a given node \(O(1)\) once the node is known, but it would still require \(O(n)\) to find that node by value, and it would consume extra memory for the backward pointer. A sentinel node at the head could simplify the empty-list and head-deletion cases, eliminating the special `self.headval is None` branch, but the starter code does not use sentinels and the task forbids changing the node-creation structure. The chosen design therefore respects the given skeleton while still covering all required edge cases.

A subtler issue is that the API takes a value rather than a node reference. If the list contains duplicate values, `Insert` always targets the first match, which may not be the caller's intention. A more precise API would accept a `Node` reference or an index, but that would complicate the calling code and is unnecessary for the rainbow example. Finally, the original `AtBeginning` helper creates a node but never links it; this is a pre-existing defect in the starter code and is not introduced by the `Insert` implementation. Overall, the solution is concise, readable, and correct for the specified operations.
